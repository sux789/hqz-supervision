## 1. 需求背景（用户原话）

> 「一个流程多个环节，用户定义，有哪些环节，每个环节会显示那些什么基本信息，提交那些信息，比如是否通过，不通过备注必填，看文档是否有近二日新增纪要，设计一个用户填的文档，后再较换为业务员填的文档，叁考 巡视，巡视可能一对多，多次，验苗可能一条记录对多少班对，验收有前后关系，只有先完成前面的 才能做后面的，有问题向我提问。业务员填写角度够全面，维度够。程序员调整后，自动生成程序」

拆成 6 条硬需求：

| # | 需求 | 落点 |
|---|---|---|
| 1 | 环节由用户（业务员）定义，不是写死 8 个 | ②环节 表，一个流程任意条数 |
| 2 | 每环节显示哪些**基本信息** | ②环节「显示的基本信息」→ 界面顶部只读信息条 |
| 3 | 每环节**提交什么**，如是否通过、不通过备注必填 | ②环节「提交方式 + 结论问法 + 不通过必填原因」 |
| 4 | 巡视 **一对多、多次**；验苗 **一条记录对多个小班** | 「作用对象 + 可填次数 + 关联小班」三列 |
| 5 | 验收环节**前后有依赖**，前面没完成不能做后面 | 「前置环节」列 + 转序闸门（且必须**通过**才放行） |
| 6 | 业务员填完 → 程序自动生效，不用改代码 | `flow_config.py` + `tools/flow_build.py --apply` |

近两日新增纪要：`doc/智能纪要：20261019_092708 2026年10月20日.md`（2026-10-20 09:35 上传），
其中的工序调整已全部落进预填内容（见 §3.6）。

## 3. 设计方案

### 3.1 三层模型（业务员只做选择题）

```
①流程  ── 一条流程 = 一种项目类型的一套验收方案（也可以是"独立入口"不挂小班）
  └── ②环节  ── 环节 = 一道工序/一次抽查/一条巡护记录
        └── ③核验项  ── 核验项 = 现场要填的一个格子（控件/单位/必填/标准来源/合格判定）
```

④选项（下拉值复用）、⑤字段字典（data 列名清单，程序生成、业务员只选不写）是配套字典。

**为什么是三层而不是两层**：业务员最熟悉的是"这道工序要看哪几个数"（③），
而程序员需要的是"每个数什么控件、必填否、跟哪个设计值比"（③ 的列）。
两层（字段塞一列用分号切）会让控件类型与必填规则无处安放，最后还是程序员返工。

### 3.2 四个维度表达"一对多 / 多次 / 前后依赖"

| 维度 | 列 | 取值 | 效果 |
|---|---|---|---|
| 作用对象 | ②环节 `作用对象` | 小班 / 苗木批次 / 材料批次 / 巡护点 / 项目 | 记录挂在谁身上；决定"一小班一档案"还是"按批次" |
| 可填次数 | ②环节 `可填次数` | 一次 / 多次 | 多次 → `flow_records.rec_no` 递增；界面出「已填 N 条 + 新增一条」 |
| 关联小班 | ②环节 `关联小班` | 不需要 / 单选 / 多选 | 多选 → 一条记录勾多个小班（验苗），不重复填 |
| 前置环节 | ②环节 `前置环节` | 环节名，多个用；分隔；空 = 上一环节 | 只等声明的那几个；且**结论必须通过**才放行 |

**关键取舍**：材料检验按批次属于「独立入口」，`挂载方式=独立入口` →
注册表写成 `条件字段=独立入口`（永不与 data 任何列相等），**不会被任何小班行自动命中**，
避免"苗木没验收就锁死造林工序"（纪要明确要求拆开）。

### 3.3 提交方式 → 结论控件（业务员不写语法）

| 提交方式 | 生成控件 | result 落库 | 是否要求验收结果 |
|---|---|---|---|
| 是否通过 | `是否通过` 下拉 + （不通过时）`不通过原因` 多行文本 | 通过 / 不通过 | 否 |
| 三档结果 | `验收结果` 下拉（合格/整改后合格/不合格） | 同左 | 是 |
| 完成情况 | `完成情况` 下拉（全部完成/部分完成/未完成） | 同左 | 否 |
| 仅记录 | 无结论控件 | 空 | 否 |

「不通过必填原因=是」时：前端不填不显示提交可用；后端 400 并逐项列出缺什么。

### 3.4 校验规则（错误带表名+行号，C02 口径）

阻断（errors，本次不生效）：
流程名未在①定义 / 序号跳号或重复 / 环节名同流程重名 / 环节类型·作用对象·可填次数·关联小班·提交方式不在白名单 /
前置环节不存在或排在自己之后（转序死锁）/ 「显示的基本信息」列名在 data 不存在 / 核验项重名 /
下拉·多选没写可选项 / 流程零环节 / 「仅记录」且零核验项（空环节） / 三张表之间流程名对不上。

提示（warnings，不阻断）：标准值来源列在 data 不存在（只能人工判定）/ 适用项目类型留空（会对全部小班生效）/
「不通过必填原因=否」风险提示 / 照片自然语言解析出 0 个按钮。

### 3.5 自动生成链路（"程序员调整后自动生成程序"）

```
业务员填 xlsx
   ↓  python tools/flow_build.py <xlsx> --check          # 校验，错误带行号
   ↓  python tools/flow_build.py <xlsx> --emit flows.json # 产出配置（可审可 diff）
   ↓  python tools/flow_build.py <xlsx> --apply <wid>    # 只改 workbooks.flows，先自动备份 db
App 打开该工作簿 → 按新流程渲染（不重新上传 Excel、不动一行数据）
```

另一条路：把 5 张表直接放进模板工作簿一起上传，`main._parse_flows` 检测到
`②环节`+`①流程` 就优先走 `flow_config.parse`（`source=user_doc`），老 12 列格式继续兼容。

### 3.6 纪要（2026-10-20）逐条落地

| 纪要要求 | 预填内容 |
|---|---|
| 边界确认只留"是否在设计范围内"，选否必填原因 | 环节 1：`结论问法=是否在设计小班范围内`、`不通过必填原因=是`，删掉 12 项勾选 |
| 整地加"整地数量"（设计 vs 现场核实） | 核验项`整地数量`，标准值来源=`总株数`（界面显示"设计值 627 / 实测"） |
| 回塘新增质量核验，删底肥品牌 | 核验项`回塘质量`（符合/不符合）+ 提示"不符合必须写具体问题"；无品牌字段 |
| 栽植/清干/覆膜/撑杆合并 | 环节 4「栽植」内置`清干覆膜撑杆`下拉，不再单独一环 |
| 苗木检验独立大项、按批次、不随小班重复 | 环节 5「苗木进场检验」：苗木批次 + 多次 + 关联小班多选，前置只等边界确认 |
| 小班档案分巡护 / 检查验收；巡护可多次不同日期 | 环节 8「日常巡护」：巡护记录 + 多次 + 仅记录；不同日期多条 |
| 竖版纵向排列，只显本工序标准 | 界面按环节只渲染本环节基本信息与核验项（`flow-basic` + 逐项纵向） |

## 6. 反转记录

1. **反转 v0.31「转序只看提交过没有」** → 改为"结论必须通过"。原因：纪要明确"有问题一定要上通知单、
   不是口头警告"，不合格也算过会让留痕形同虚设；且整改后重交通过即可放行，不会真卡住现场。
2. **反转 v0.31「每个环节都必填验收结果」** → 「仅记录 / 是否通过」环节不再要求。原因：巡视记录没有
   "合格/不合格"概念，硬塞的下拉让巡护永远提交不了。
3. **反转 v0.31「单行文本一律选填」** → 新格式按 ③核验项「必填」列判定。原因：进场批次号是必填的。
   （老格式无 `required` 键，仍走旧口径，不动线上已有流程。）
4. **反转 doc/019 §五 坑 3 的处理方式（只提示不改配置）** → 业务员文档里「适用项目类型」留空会变成
   无条件流程，仍只给 warning 不阻断（配置意图可能是"全部小班"），但文案写清后果。
5. **`数值×3` 仍保留旧结构**（`sub=[名字+长/宽/深]`）：前后端都按 sub 取值，不各自拼字符串（C19 教训）。
