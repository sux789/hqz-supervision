## 1. 需求背景（用户原话）

> 执行性价比高的优化，优化逻辑与代码 文档,比如main.py 太大 ；规划下一步迭代

落地为：只做**不改口径、不引新依赖**的结构性拆分——把 main.py 里「纯解析」和「流程判定」
两块积木迁到独立模块，main.py 只留路由与编排；同时产出下一步迭代规划。

## 2. 验证结果（改前数据对比/报错现场）

改前实测（`bash tools/ai.sh map`）：

| 文件 | 行数 | 符号数 | 最大函数 |
|---|---|---|---|
| `main.py` | 3202 | 101 | `api_flow_save` 307 行 / `api_flow_batch` 227 行 / `init_db` 167 行 |
| `param_parser.py` | 468 | 15 | `parse_params` 137 行 |
| `flow_parser.py` | 489 | 17 | `parse_att` 75 行 |

问题不是"文件行数"本身，而是三类职责混在一个命名空间里：

1. **纯函数**（xlsx → 数据、流程命中 → payload）与 Flask 请求上下文、SQLite 连接纠缠，
   单测只能整包 import main（连带建库、建目录），复用与定位成本高。
2. 同名逻辑跨文件复制粘贴无约束：`json.loads(r['flows'] or '{}')` 在 `api_get` 与
   `_wb_flows` 各写一份。
3. 头部 docstring 仍写「B1 本地预览版」，与实际能力（线上多用户、流程引擎）不符。

## 3. 设计方案（逻辑+口径依据）

**原则**：只搬代码、不改行为；每个新模块的依赖方向单向，禁止反向 import main。

```
param_parser / flow_parser / flow_config / flow_tpl   （解析积木，无 Flask）
        ├── wb_parse.py       xlsx → (sheet, headers, rows, config, param_rows, key, flows_json)
        └── flow_hit.py       流程命中/判定/附件闸门（纯函数；仅 _tpl_hit 读 flow_records）
main.py                       路由 + DB + 鉴权 + 导入导出编排
```

- **B4/B5 迁入 `wb_parse.py`**：整块不依赖 Flask/DB，可直接单测；常量
  `PARAM_SHEET/DATA_SHEET/META_SHEETS` 随迁，避免两处定义。
- **B19/B29/B30/B31 的判定逻辑迁入 `flow_hit.py`**：除 `_tpl_hit` 需要读
  `flow_records`（v2 路由状态）外全是纯函数。DB 连接用 `set_db(main.db)` 注入——
  **不采用 `from main import db`**，否则循环导入；注入还保证测试里
  `_M.DB_PATH = tmpdb` 仍然生效（`db()` 读的仍是 main 模块全局）。
- **main.py 保留同名 re-export**（`from wb_parse import ...` / `from flow_hit import ...`）：
  测试与外部工具通过 `main.parse_workbook_storage`、`main._flow_hit` 的既有入口不破。
- **不整体拆路由**：`api_flow_save/api_flow_batch` 与 `bp`、`db`、鉴权强耦合，
  一次性搬迁风险高于收益；列入下一迭代（见 §8），届时先补路由级 smoke test 再动。
- **顺手去重**：`api_get` 的 flows 解析改调同文件 `_wb_flows`；删除迁移后不再使用的
  导入（`ast/operator/zipfile/flow_parser/flow_tpl/parse_params/percent_cols_of/PARAM_KEYS/date`）。
