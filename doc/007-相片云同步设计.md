# 007 - 相片云同步设计（服务器接收 → 腾讯 COS 暂存 → 百度网盘）

> 状态：**设计评审稿，未实现**。用户原话驱动，先评审可行性，确认后再排里程碑。

## 1. 需求背景（用户原话）

> 相片同步，参考 /Users/sux/Desktop/trans_v2 同步到百度云的 app 同名目录下，是否可行？插件方式，比如后台设置压缩参数，设置同步平台，这样是否可行？如果可行，后台就设置同步参数，启动同步参数才同步，百度云参数也在后台配置中，先用 trans_v2 作为默认，评审和优化我的思路。

## 2. 可行性评审结论

**结论：可行，且「COS 暂存 + 状态标记」链路比纯中转更稳，推荐采纳。**

### 2.1 trans_v2 复用评估（已核实）

trans_v2 `cloud/baidu_pan.py` 是完整的百度网盘开放平台客户端，可直接移植：

| 能力 | 状态 | 说明 |
|---|---|---|
| OAuth 授权 | ✅ | get_auth_url + exchange_code，token 持久化 JSON |
| token 自动续期 | ✅ | refresh_token 有效（30 天期），_refresh_token 现成 |
| 分片上传 | ✅ | precreate → superfile2（4MB/片）→ create 三步走 |
| 已存在覆盖 | ✅ | 先删后传，处理了 `_YYYYMMDD` 副本坑 |
| 列目录/分享/配额 | ✅ | 后台状态面板可直接用 |

移植方式：复制进 `sync/baidu_pan.py`，剥离 `infra.debug / infra.error_codes / infra.if_throw` 依赖（约 3 处调用，改为标准 logging/异常）。百度应用凭证复用 trans_v2 的同一套 app_key/secret（授权一次即可）。

### 2.2 链路方案对比

| 方案 | 链路 | 可靠性 | 复杂度 | 磁盘/费用 | 结论 |
|---|---|---|---|---|---|
| A 纯中转 | 手机→服务器→百度 | 低：野外信号差，百度推送失败即丢（手机相册兜底） | 最低 | 零 | 否 |
| B 服务器磁盘队列 | 手机→服务器→本地 pending→百度 | 中：服务器磁盘/重置风险 | 低 | 服务器磁盘（每张 300-500KB） | 备选 |
| **C COS 暂存（用户提出）** | 手机→服务器→**COS**→百度 | **高：COS 高可用，百度推送失败可无限重试，断点可续** | 中 | COS 费用极低（GB 级每月几元） | **推荐** |

C 方案的核心优势：**手机端只依赖第一跳**——照片传到服务器/COS 成功即安全，剩下的百度推送由服务器慢慢补，与野外网络状况解耦。且 forest.bibook.top 本就在腾讯云，服务器→COS 同区域内网快、免流量费。

### 2.3 风险与对策

| 风险 | 对策 |
|---|---|
| 双云凭证配置（COS SecretId/Key + 百度 app_key/secret） | 全部收口在后台「同步设置」，未配置则开关不可开启 |
| 百度 API 频率限制 | 推送间隔 1s/张；批量补推走队列限速 |
| COS 副本清理 | 百度成功后默认**保留 30 天再清**（兜底灾备），后台可改「永久保留/立即删除」 |
| token 失效 | refresh_token 自动续期；续期失败 → 后台标红提示重新授权 |
| 重复上传（重试导致网盘重名副本） | 百度 precreate 幂等：同一 remote_path + md5 秒传/已存在直接返回（trans_v2 已处理） |
| C07 冲突 | 修订为「照片不在服务器**长期**存储」：成功即删暂存，暂存只存在于 COS（服务器不留副本） |

## 3. 架构与状态机

```
手机拍照（压缩+水印，现有链路不变）
  ├─ 存系统相册 / 浏览器下载        ← C07 本地链路保留，不变
  └─ 同步开关开启时 → POST /api/photo（multipart，≤500KB）
        │
        ▼
服务器接收（不落服务器磁盘，直接内存转发）
  │  写 photo_sync 记录 state=received
  ▼
上传腾讯 COS  ←→  失败重试（photo_sync.retry_count++）
  │  成功 → state=cos_ok（COS key: {网盘应用目录}/{参数目录}/{文件名}.jpg）
  ▼
后台推送百度（懒触发：新照片到达时尝试一次；否则积压等手动/定时）
  │  从 COS 拉回内存 → BaiduPan 三步上传 /apps/{app_dir}/{参数目录}/{文件名}.jpg
  │  成功 → state=baidu_ok（终态，按生命周期策略清理 COS 副本）
  ▼
网盘目录与手机相册镜像：/apps/{app_dir}/{sheet名称}/{小班号}/{相片文件名}.jpg
```

状态机（photo_sync.state，单向推进，每步幂等）：

```
received → cos_ok → baidu_ok(终态)
    └──────┴─ 失败留在当前态，retry_count++，last_error 记录
```

后台「同步状态」面板：按状态计数（received/cos_ok/baidu_ok），可按工作簿过滤，单张/批量手动重推。

## 5. 后台「同步设置」UI（admin 新增卡片）

1. **同步开关**：默认关。开启前置校验：COS 四项 + 百度 app_key/secret + 已授权，缺一不可。
2. **平台**：baidu（默认）/ qiniu（预留，trans_v2 有先例）。
3. **COS 配置**：SecretId / SecretKey / Bucket / Region。
4. **百度配置**：app_key / secret_key / 网盘应用目录（默认 /apps/supervision_photos，与 trans_v2 的 book_translator 分开）。
5. **授权按钮**：生成授权 URL → 管理员浏览器授权 → 粘贴 code → 换 token 存 settings，之后自动续期。
6. **同步状态面板**：三态计数 + 最近失败列表 + 单张/批量重推 + COS 保留天数。

## 6. 参数 sheet 新增 key（压缩参数下发，C01 参数驱动）

| key | 类型 | 默认值 | 说明 |
|---|---|---|---|

## 7. API 设计

| 路由 | 方法 | 说明 |
|---|---|---|
| /api/photo | POST | 用户端拍照中转（multipart: file + workbook_id + filename + subdir）。开关关 → 423 明确提示；成功即返回，后续推送与手机无关 |
| /admin/api/sync/settings | GET/POST | 读写同步配置（secret 返回时打码） |
| /admin/api/sync/auth_url | GET | 生成百度授权 URL |
| /admin/api/sync/auth | POST | 粘贴 code 换 token |
| /admin/api/sync/status | GET | 三态计数 + 最近失败 |
| /admin/api/sync/retry | POST | 手动重推（ids 或全部 cos_ok） |

推送触发：新照片 cos_ok 后立即尝试一次百度推送；失败留给积压，管理员手动重推（**不引入常驻定时进程**，保持 Flask 单进程轻量；将来量大再加 APScheduler）。
