# 015-编辑不丢（v0.28 保存可靠性重做）

> 版本：v0.28 ｜ 日期：2026-09-17 ｜ 状态：已实现并本地实测通过
> 关联约束：**C17（新增）**、C14、C08

## 一、现象与上次为什么没修好

用户第二次报："验收备注结果还是丢，填备注，再切换回来，app 上见不到刚填写的备注。"

v0.25 我修了三条（离场冲刷 / 快照 wid-ridx / 逐键捕获），但**其中第三条建立在错误假设上**：

> 我当时假设"jspreadsheet 的编辑器会派发能被外部监听的 `input` 事件"，
> 并据此加了委托监听 `#formEl` 的 `input` 当作"逐键捕获"。

**这个假设没有被真正验证过。** 我 v0.25 的"验证"是：自己 `createElement('input')`、
赋个值、`dispatchEvent(new Event('input'))`，然后看到 `allRows` 更新了 ——
那只证明"监听器存在且能工作"，**完全没有证明真实键入会触发它**。

本次想复现时发现：在无头浏览器里连单元格都点不进编辑态（零事件），进一步说明
**"靠事件捕获"这条路本身不可靠**；翻 `static/vendor/jspreadsheet.min.js` 也只能确认它会
`createElement("input")`，无法确认它是否派发 `input`。→ 不能把关键数据押在第三方组件的
事件行为上。

## 二、v0.28 的做法：三条都不依赖编辑器实现

| # | 机制 | 解决什么 |
|---|---|---|
| ① | **`syncGridIntoAllRows()`**：任何离场/切后台时刻，**直接从 DOM 读回值**（td 里有编辑器 `<input>` 就取它的 `value`，否则取 td 文本），写进 `allRows` | 编辑器还没提交（它自己的 `onchange` 未触发）也能拿到最新内容。**不再关心它发不发事件** |
| ② | **文档级捕获监听** `input` / `keyup` / `focusout`（`capture: true`） | 命中值格就先同步进内存。捕获阶段意味着不管编辑器怎么处理事件，我们都能先拿到 |
| ③ | **落盘草稿**：每次改动把 `{wid, ridx, values, ts}` **同步写进 `localStorage`**；启动 / 切回前台时若有草稿就**自动补交** | **进程被杀 / 页面被系统重载**时，草稿仍在（localStorage 是同步写入，不随页面死）。补交成功才清草稿 |

配套：

- `buildSaveJob()`：优先用已排队任务；**若没排队但 DOM 与"已保存版本"有差异**，也照样组装任务
  （覆盖"onchange 压根没触发"）；`flushRowSave()` 成功后把 `cur.rows[ridx]` 同步成新值，
  避免每次都判成"有差异"而重复保存。
- `flushRowSaveUnloading()`：**先写草稿再发 keepalive 请求** —— 万一请求也没出去，下次还能补交；
  请求成功（`.then(r => r.ok)`）才清草稿。
- `visibilitychange`：**hidden → 先 `syncGridIntoAllRows()` 再冲刷**（顺序很关键：切后台时编辑器
  往往还没提交，不先收值就等于什么都没存）；**visible → `submitDraftIfAny()`**（国产 ROM 在后
  台会冻结定时器，回来立刻补交）。
- 草稿超过 12 小时不再自动补交（避免覆盖别人后来的修改），直接丢弃。

## 三、验证（浏览器实测，逐条可复现）

| # | 步骤 | 结果 |
|---|---|---|
| ① | 直接把值写进值格的 DOM，调 `syncGridIntoAllRows()` | `changed=true`，`allRows` 同步 ✅ |
| ② | 在值格里派发真实 `input` 事件（捕获阶段） | `allRows` 同步、生成 `pendingSave`、**草稿已写入 localStorage** ✅ |
| ③ | 调 `flushRowSave()` | 服务端落库、草稿清空、`cur.rows` 同步 ✅ |
| ④ | **造"已写草稿但没发出去"的状态 → 重载页面（模拟进程被回收后重开）** | 启动时**自动补交**：服务端备注从旧值变为 `被杀前填的备注-2026`、草稿清空、toast「已补交上次未保存的修改」✅ |
| ⑤ | 控制台 | 无报错 ✅ |

第 ④ 条正是用户报的场景（切走 → 回来 → 内容没了），现在**即使页面被系统重载也能补回来**。

全量回归：单元 68 + 端到端 80 = **148 项全绿**。

## 四、诚实交代：v0.25 我"验证"过头了

v0.25 的迭代文档里我写"逐键捕获已验证：向值格派发 `input` 事件 → `allRows` 立即同步"。
事实是：那次派发的是**我自己造的 input 元素**上的事件，不是真实键入，也不是编辑器产生的。
**这类"自己造事件喂给自己的监听器"的验证是自证循环，不能算数。** 教训已写入 C17。

正确的验证顺序应该是：先确认"真实输入路径会产生什么事件 / 值最终存在哪个 DOM 节点"，
再据此设计捕获方式 —— 本次就是先接受"无法确认"，改用"不依赖事件、直接读 DOM + 落盘草稿"。

## 六、附：v0.28.1 —— "视频保存后华为弹出应用信息"的根因与修复

用户原话："视频保存后，华为会弹出应用信息。" 追问确认是**权限引导弹窗**（不是崩溃弹窗）。

### 6.1 证据链

```
ensurePermissionsUpfront()            ← JS，在 boot() 里调用
   └─ plugin.ensureBackground()       ← 原生
        ├─ requestIgnoreBatteryOptimizations(pkg)   → 弹「电池优化白名单」系统对话框（仅当不在白名单）
        └─ openAutostartSettings()                  → 跳华为「自启动/后台运行管理」页（**无条件**！）
```

而 `ensurePermissionsUpfront()` 的准入判断是：

```js
let permsAsked = false;             // ← 只存在内存里
async function ensurePermissionsUpfront() {
  if (permsAsked) return;
  permsAsked = true;
  ...
```

**`permsAsked` 是内存变量，页面一重载就归零。** 录像走系统相机时，华为省电策略常把页面重载
（这正是 v0.18 引入保活前台服务的背景），回来后 `boot()` 再跑一遍 →
**又弹一次电池优化对话框 + 又跳一次自启动页**。这就是用户看到的"视频保存后弹出应用信息"。

### 6.2 修复

| 侧 | 改动 | 是否需要重新出包 |
|---|---|---|
| JS | `permsAsked` 改为**按安装持久化**：`localStorage['hqz_sup_perms_asked_v1']`（键名带版本号，将来要重新引导升版本号即可）；进入函数**立刻**写标志，中途失败也不重复骚扰；新增 `supAskPermsAgain()` 供手动重置（排查/用户反馈权限没给全时用） | 不需要（改的是网页端） |
| 原生 | `resolveBackground()` 里 `openAutostartSettings()` 由**无条件跳**改为 `ignoring ? false : openAutostartSettings()` —— 已在电池优化白名单就不再跳引导页 | **需要重新出包才生效** |

> 也就是说：**现在（v0.28.1 上线后）症状就会消失**，因为 JS 层已经保证不再重复调用引导；
> 原生那行是"把根治也补上"，等下次出 APK 时一并生效。

### 6.3 验证（浏览器）

| 步骤 | 结果 |
|---|---|
| 登录（`boot()` 跑过） | `localStorage['hqz_sup_perms_asked_v1'] = '1'`，`permsAsked = true` ✅ |
| 重载页面（模拟录像返回重载） | 标志仍在，`permsAlreadyAsked() = true` → **会跳过引导** ✅ |
| 再重载一次 | 仍稳定跳过 ✅ |
| `supAskPermsAgain()` | 返回「已重置，将重新引导一次权限」并重新引导 ✅ |
| 控制台 | 无报错 ✅ |
