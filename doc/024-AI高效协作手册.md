# 024 · AI 高效协作手册（人机对齐 · 多 Agent 并行）

> 版本：v1.0 ｜ 日期：2026-10-18 ｜ 适用：本项目全部改动
> 关系：`AGENTS.md` 是入口指针，本文件是**方法与判据**；`CONSTRAINTS.md` 是硬规则，`BLOCKS.md` 是坐标，
> `STATE.md` 是现状。四者不重复：本文件回答「**为什么这样做、什么时候该改**」，其余回答「**是什么**」。
> 一句话：**AI 开发的天花板不是模型能力，是「约束被执行的确定性」。**
> 把确定性拆开，就是三个可拧的旋钮、三本不许混的账、四条不许破的并行铁律。

## 1 一个公式，三个旋钮

一次改动的总成本，近似等于：

```text
返工成本 ≈ （歧义度 × 影响面） ÷ 反馈延迟
```

- **歧义度**：人和 AI 对「改哪个字段、什么算改好」的理解偏差。
- **影响面**：一次改动可能碰坏多少东西（文件数、调用方、线上数据）。
- **反馈延迟**：从改错到发现改错之间隔了多久（编辑器 / 提交 / 推送 / 线上）。

这不是修辞。它是一条**取舍判据**：任何「要不要投入做某件事」的决策，先问它拧的是哪个旋钮。
一个都不拧的事，不做——哪怕它看起来很像工程。

| 做法 | 拧哪个旋钮 | 成本 | 本项目对应 |
|---|---|---|---|
| 指令坐标化（积木 → 文件:行 → 字段） | 歧义度 ↓↓ | 10 秒 | §4 指令模板、`tools/ai.sh map` |
| 术语表 + 契约表 | 歧义度 ↓ | 已沉没 | `GLOSSARY.md`、`BLOCKS.md` |
| 文件所有权 + 行范围租约 | 影响面 ↓↓ | 30 秒/任务 | §5、`tools/ai.sh task` |
| 一版 1–3 个问题 | 影响面 ↓ | 习惯 | `AI_INSTRUCTIONS` 迭代纪律 |
| 提交前 2 秒闸门 | 反馈延迟 ↓↓ | 已沉没 | `tools/hooks/pre-commit` |
| 推送前全量回归 7 秒 | 反馈延迟 ↓ | 已沉没 | `tools/hooks/pre-push` |
| 再写一份「开发规范」文档 | **不拧** | 半天 + 每会话上下文 | 不做 |

**反直觉结论**：文档写得越多，不一定越对齐；**只有被机器在正确时机强制执行的那部分，才会真正对齐**。
所以本手册的每条方法必须能指向一个载体（命令 / 断言 / 钩子 / 表），指不到的就不写进来。

## 2 三本账：AI 只能改一本

| 账 | 内容 | 谁能改 | 载体 | 判据 |
|---|---|---|---|---|
| **事实账** | 代码、模板、数据、测试 | AI 可改（过闸门） | git 工作区 | 闸门全绿 |
| **判断账** | 约束、契约、术语、口径、优先级 | **只有人**（或人明确授权的集成者） | `CONSTRAINTS` / `BLOCKS` / `GLOSSARY` / 本文件 / `doc/NNN` | 有反转链与拍板记录 |
| **过程账** | 简报、评审单、分诊、任务卡、看板 | **只有机器**（命令生成） | 派生视图（不入 git） | 可随时重建，禁止手改（C23） |

三条边界，违反任意一条都会长出「第二份真相」：

1. **AI 不许把过程账写成判断账**：任务卡里的猜测、评审单里的推断，都不是约束；要升级为约束必须人拍板。
2. **AI 不许改判断账来让闸门变绿**：改断言、改约束、改术语定义去迁就代码，是最贵的错误（掩盖而非修复）。
3. **人不许手改过程账**：手改 `brief.md` / `review.md` / `last_gates.json` 等于制造一个会过期的假状态；
   要变就改源文件再重跑命令。

这条划分解决了一个长期困扰：**「AI 说它改好了」为什么不可信**——因为它只能对事实账负责，
而「改好了」的定义在判断账里，必须由人先写死、再由机器判定。

## 3 上下文分层：把「读什么」变成预算

AI 每会话的上下文不是免费的：读得越多，注意力越散，越容易漏掉最关键的 3 行。
所以按**读取频率**分三层，每层只有一个入口：

| 层 | 内容 | 预算 | 何时读 | 载体 |
|---|---|---|---|---|
| **L0 常驻** | 现在能不能提交 / 不能违反什么 / 下一步 | **≤4KB** | 每会话第一件事 | `doc/brief.md`（`bash tools/ai.sh brief`） |
| **L1 按需** | 入口文件（协议、约束索引、积木、术语、状态） | 合计 ≤36KB | 简报指到哪条读哪条 | 根目录 6 个 `.md` |
| **L2 检索** | 约束详解、迭代史、决策依据、代码符号 | 无上限 | 出事 / 改具体模块时 | `doc/023`、`doc/NNN`、`git log`、`doc/map.md` |

三条硬规则：

1. **每会话必读的东西必须 ≤4KB 且只有一份**。两份 = 迟早不一致。
2. **只在出事时读的东西不许进根目录**。根目录膨胀等于每会话多烧一遍上下文。
3. **派生视图不手改**（C23）：`brief` / `review` / `TRIAGE` / `last_gates.json` / `map` / `board` / `align.html`
   全部由命令生成，`.gitignore` 已排除；要改就改源，再重跑。

现状（`bash tools/run.sh` 的门 6 会持续校验）：

```text
入口 6 文件   30KB / 36KB
brief        3.7KB / 4KB
回归          237 项 / 6.4s
```

> 为什么 brief 值得单独做一层：跨会话恢复的真实成本不是「读 30KB」，而是「读完 30KB 仍不知道现在该干什么」。
> 简报强迫我们提前想清楚「现在 / 必须知道 / 下一步」——**这个思考本身就是对齐**。

## 4 需求 → 改动：六步流水线

「需求修改高效」不是让 AI 写得更快，而是让**一次改对**。六步，每步都有失败信号：

| # | 步骤 | 做什么 | 产物 | 失败信号（出现就退回上一步） |
|---|---|---|---|---|
| 0 | 收需求 | 一句话说清「谁在什么场景要什么」 | 一句话 | 说不清 → 先问，不动手 |
| 1 | 定位 | 积木号 → 文件 → 符号行 | `doc/map.md` 查到的行号 | 定位不到 → 说明理解错了需求 |
| 2 | 划边界 | 任务卡：范围（文件:行）+ 验收命令 + 禁改清单 | `.agent/tasks/T-xxx.json` | 范围超过 1 个文件 → 拆任务 |
| 3 | 最小改动 | 只改范围内的行；不顺手重构 | diff | diff 里出现"顺便" → 撤回 |
| 4 | 过闸门 | `bash tools/run.sh` | `last_gates.json` | 红 → 分诊，不许改断言 |
| 5 | 归因 | 差异/失败先分类：代码 / 数据 / 口径 / 环境 | 评审单「待拍板」 | 直接改代码对齐 → 停手 |
| 6 | 留痕 | `doc/NNN` 七段式 + `Refs: doc/NNN` + 更新 STATE | 提交 | 缺 Refs → 钩子拒绝 |

### 4.1 指令模板（人 → AI，复制改括号）

```text
目标：[一句话，谁在什么场景要什么]
坐标：B[积木号] → [文件:行号] → [字段名/接口/单元格]
边界：只改 [文件:行范围]；不改 [模板/数据/口径]；不顺手重构
验收：bash tools/run.sh 全绿 + [本需求的专属判据，可观测]
不确定：列出「问题 / 候选 / 建议 / 依据」，我批量裁决，不要猜
```

### 4.2 模糊指令的代价（真实对照）

| 模糊写法 | AI 的实际行为 | 代价 | 改写 |
|---|---|---|---|
| 「把导出修一下」 | 猜一个最像的地方改 | 来回 3 轮 + 可能改坏别的 | 「导出工作表头多了空列，`main.py::api_export` 的 `headers` 生成处」 |
| 「优化一下性能」 | 加缓存、改结构 | 引入跨请求状态（违反「每次运行全新状态」） | 「600 行工作簿首屏 ≥3s，先测 `/api/workbooks/<id>` 耗时再定」 |
| 「检查一下有没有问题」 | 生成一份乐观报告 | 等于没检查 | 「跑 `bash tools/run.sh`，把 FAIL 逐条列出来」 |
| 「照这个思路做」 | 各自理解不同 | 返工 | 先写 5 行方案，确认后再动手（>3 文件强制） |

### 4.3 需求进来先做一次「三问筛选」

1. **是不是口径问题**（谁算对）？→ 是 → 先改 CONSTRAINTS + 迭代文档，代码最后动。
2. **是不是数据问题**（样例本身脏）？→ 是 → 不动代码，出数据体检报告。
3. **是不是只在特定设备/特定工作簿出现**？→ 是 → 先拿现场（日志 / 截图 / 工作簿 id），不猜。

## 5 多 Agent 并行协议

前提：并行的收益是**吞吐**，代价是**冲突**。冲突的成本远高于吞吐的收益，所以并行只有在
「范围不重叠 + 契约先定 + 合并有序」三条同时成立时才允许。

### 5.1 四条铁律

1. **一个文件同时只有一个 owner（租约）**。两个 agent 改同一文件 = 冲突必然发生，只是什么时候发现的问题。
2. **契约先行**：接口路径、请求/响应字段、错误码、参数 key，先写进任务卡，再各自实现。契约没定就并行 = 造两套。
3. **合并顺序由人定**。Agent 只提交自己的分支/改动，不自动 merge、不自动 rebase 别人的成果。
4. **入口文件只许集成者改**：`AGENTS` / `AI_INSTRUCTIONS` / `CONSTRAINTS` / `BLOCKS` / `GLOSSARY` / `STATE`。
   Worker 把「建议补丁」写进任务卡 notes，由集成者在合并时一次性落盘——否则并行改同一段文档必冲突。

### 5.2 为什么按「文件 + 行范围」分，而不是按「功能」分

功能是人的语言（"做导出"），冲突发生在文件上（`main.py`）。
按功能分工，两个 agent 会各自认为自己拥有 `main.py` 里"自己那部分"，然后在同一文件里互相覆盖。
**能机器判定的边界只有文件与行号**，所以任务卡的范围必须写成 `main.py:1780-1830` 这种形式。

### 5.3 本项目的天然分区

| 区 | 文件 | 典型任务 | 并行风险 |
|---|---|---|---|
| A 后端 | `main.py` | 接口、导出、鉴权、审计 | **瓶颈区**：单文件 2077 行，**同时只许 1 个 agent** |
| B 参数契约 | `param_parser.py` | 新 key、语法、合并逻辑 | 高（影响所有工作簿），一次只动一个 key |
| C App 前端 | `static/app.js`、`style.css` | 填表、拍照、保存、轨迹 UI | 中（1937 行，按行范围切） |
| D 流程前端 | `static/flow.js` | 验收 8 环节界面 | 低（独立模块，最适合并行） |
| E 后台 | `static/admin.js`、`templates/admin.html` | 模板管理、压缩、同步 | 低 |
| F 原生 | `android/**` | 轨迹、录像、权限 | 低，但**必须出包**（versionCode 递增） |
| G 工具/文档 | `tools/**`、`doc/**`、`tests/**` | 闸门、脚本、迭代文档 | 低，但改测试要单独说明 |

**结论**：真正可以同时开工的组合是 `D + E`、`C + F`、`G + 任意`；`A + A`、`B + B` 永远串行。
这不是保守，而是把「已知必然冲突」提前变成规则，省掉一次半夜的三方 diff。

### 5.4 标准流程（五条命令）

```bash
# 1 建卡（划边界，30 秒）
bash tools/ai.sh task new --title "验收照片按钮支持 PDF" \
     --scope "static/flow.js:120-260,main.py:1420-1470" --by claude --accept "bash tools/run.sh"

# 2 认领（有重叠会当场拒绝）
bash tools/ai.sh task claim T-20261018-01 --by claude

# 3 干活：只读 brief + 自己的卡，不读全仓
bash tools/ai.sh brief

# 4 验收
bash tools/ai.sh explain && bash tools/run.sh

# 5 交付
bash tools/ai.sh task done T-20261018-01 --note "已合并，见 doc/026"
bash tools/ai.sh task list          # 全局视角
```

### 5.5 什么时候需要 worktree

| 场景 | 做法 |
|---|---|
| 同一台机器、两个会话、范围不重叠 | 共享工作区即可，靠任务卡租约 |
| 需要各自跑测试 / 各自改依赖 | `git worktree add .worktrees/T-xxx -b feat/T-xxx`，各自 `bash tools/run.sh` |
| 一方改动会让另一方测试变红 | **不要并行**，串行 |

Worktree 注意事项：`.agent/` 在主工作树（任务卡不随 worktree 复制），合并前先 rebase 到最新 main，
集成者合并后**必须重跑一次全量闸门**（两个各自绿的改动合并后可能不绿）。

### 5.6 发现重叠怎么办（按顺序选）

1. **拆范围**：把整文件改成具体行段，多数冲突是因为懒得起行号。
2. **改成契约 + 桩**：A 先定接口返回结构，B 按桩开发，最后一方接线。
3. **串行**：A 完成后 B 再开工（最省心，代价是时间）。
4. 绝不做的：口头约定「你先改，我等你 push」——没有记录，必然有人忘。

### 5.7 并行的反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 两个 agent 同改 `main.py` | 覆盖/半合并，症状像"逻辑随机失效" | 串行，或用 `map` 切行号 |
| 各自建约束/各自改术语 | 判断账分叉，下次会话无所适从 | 写进任务卡 notes，集成者统一落盘 |
| 各自改测试让本分支变绿 | 合并后互相抵消，回归失效 | 测试只许新增，不放宽（C24） |
| 合并后不重跑闸门 | 两个绿的合并出红，线上才发现 | 集成者合并即跑全量 |
| 用「功能」描述范围 | 边界不可判定 = 没有边界 | 文件:行号 |

### 5.8 场景走查：两个 agent 同时开工

需求 A：导出增加「成活率」列（区 A 后端）
需求 B：验收环节加「整改照片」控件（区 D 流程前端）

```text
人：把两条需求拆成两张卡，A 范围 main.py:1980-2030，B 范围 static/flow.js:320-420
    + 契约：B 需要后端新增字段 survival_rate，先写进 A 的卡（契约先行）
A：认领 A → 实现字段与导出 → gates → 交付
B：认领 B → 用桩数据 {survival_rate: 0.85} 先做 UI → gates → 交付
人：按 A → B 顺序合并 → 跑全量闸门 → 更新 STATE 与迭代文档
```

两张卡范围不重叠、契约先定、合并有序——这才叫并行；否则只是"两个人同时改一个仓库"。

## 6 人机对齐：三锚点 + 三问 + 一个回路

### 6.1 三锚点（对齐靠结构，不靠记性）

| 维度 | 锚点 | 机制 | 失效症状 |
|---|---|---|---|
| **词一致** | `GLOSSARY.md` | 一个术语一个可判定定义；指令/代码出现即以本表为准 | 同一句需求两种理解，来回确认 |
| **契约一致** | `BLOCKS.md` + 任务卡 | 积木入口出口 + 五要素（类型/前置/后置/错误/副作用） | 改 A 坏了 B，谁都不知道为什么 |
| **完成一致** | `AI_INSTRUCTIONS` 的 DOD | ★ 项由 `tools/run.sh` 判定，人不许替它判断 | 「我觉得差不多了」然后线上报错 |

### 6.2 三问（人验证对齐是否成立，30 秒）

1. **现在能不能提交？** → `bash tools/ai.sh brief` 第一行 / `bash tools/run.sh --fast`
2. **这版改了什么、风险多大？** → `bash tools/ai.sh explain`（风险等级由规则算，不是模型说）
3. **红了先做什么？** → `bash tools/ai.sh triage`（事实 + 候选原因 + 处置顺序，不含结论）

三问都能在 30 秒内得到**可复现**的答案，才算对齐；任何一问只能靠"问 AI 它说没事"，就是没对齐。

### 6.3 对齐回路（不可省的一步）

```text
需求 → （>3 文件或动数据结构）5 行方案 → 人确认 → 动手 → 闸门 → 评审单 → 人拍板 → 提交
```

跳过"人确认"省下的 5 分钟，通常会在返工时花掉 50 分钟。**方案不必长，但必须写清：改哪里、不改哪里、怎么验证。**

### 6.4 双方各守三个动作

- **人**：① 指令到三级坐标；② 要求「待确认清单」而非猜测；③ 大改先看方案。
- **AI**：① 遇错先跑真实报错；② 改前读原文，不凭记忆；③ 完成后跑一条命令，不替闸门下结论。

## 7 闸门：把「做完」变成机器事实

### 7.1 七门（本项目实装，不是照抄模板）

| 门 | 检查 | 证明什么 | 耗时 |
|---|---|---|---|
| G1 回归 | `tests/run_all.sh`（单元 108 + e2e 109 + EXIF 20） | 没改坏旧行为 | 6.4s |
| G2 JS 语法/C22 | `node --check` + 禁用语法扫描（`??` `?.` `replaceAll` `Array.at`） | 老内核不会整脚本挂掉 | 0.1s |
| G3 索引一致性 | `BLOCKS` 文件存在 / `doc` 编号可解析 / 编号不重复 | 索引没腐化 | 2ms |
| G4 占位符 | 入口文件无 `[中文占位]` | 项目信息填全了 | 1ms |
| G5 密钥 | 签名/密钥文件未入库 + 私钥/AK 模式扫描 | 仓库级事故不发生 | 30ms |
| G6 上下文预算 | 入口 ≤36KB、brief ≤4KB | 每会话成本可控 | 0ms |
| G7 模板体检 | `tools/check_template.py` | 客户模板的 FATAL 可见 | 30ms |

**明确不做的门**：`validate / check_invariants / compare`（数据管线双跑对比）。
本项目没有"生成输出目录"，回归等价物就是 G1。照搬模板会让 AI 每天跑三个永远 SKIP 的门——
**SKIP 的门不是防线，是噪音**。

### 7.2 判定与措辞分离（C25）

机器只认 `gates[].id + status`（`PASS/FAIL/WARN/SKIP`），人读中文 detail。
好处：改文案不会崩下游；`brief` / `triage` / 钩子 / 未来的 CI 都读同一份 JSON，不必 `grep` 中文。
`--json-only` 给机器，默认输出给人——两种消费者，一份事实。

### 7.3 分层（按人的耐心，不按重要性）

| 时机 | 跑什么 | 耗时 | 为什么在这 |
|---|---|---|---|
| 保存/编辑 | 不跑（但 `pre-commit` 会兜底） | 0 | 编辑器里打断人=关掉检查 |
| `pre-commit` | 静态四门 + staged JS 语法 + 生成物拦截 | <2s | 天天过，必须无感 |
| `pre-push` | 七门全量（含 237 项回归） | ~7s | 一次推送一次，等得起 |
| 手动 | `bash tools/run.sh` | ~7s | 交付前、合并后、怀疑时 |

**任何一层超过人的耐心，人就会 `--no-verify`，那一层等于没有。** 所以慢门一律下沉，不并行堆在提交时。

### 7.4 WARN / SKIP 政策

- `WARN`（如模板 FATAL）：**可以提交**，但必须在迭代文档写「为什么不处理、谁处理」。
- `SKIP`（缺前置条件）：不假装通过；同一门连续 3 次 SKIP，视为该门该退役或该修（不是"永远跳过"）。
- `FAIL`：不许提交；不许改断言/改约束把它变绿；先分诊再动手。

## 8 越长越简单：反熵机制

「开发时间越长，开发越简单」不会自然发生。默认趋势是越写越乱。要它成立，必须人为设三条出口。

### 8.1 复杂度只许进三个口

| 允许增长的地方 | 为什么 | 约束 |
|---|---|---|
| 约束表 `CONSTRAINTS.md` | 每条约束 = 一次事故的沉淀，只增不改（被推翻标反转） | 一行一条，可判定 |
| 测试 | 每个修复配一条断言 | 只许新增，不许放宽 |
| 闸门 | 高频人工动作机器化 | 单门 <2s（提交层） |

**代码复杂度必须有出口**：新增能力优先「改参数 / 加分支」，而不是「加一层抽象」。
抽象只在**第三次**重复时引入（Rule of Three），且必须同时删掉被替代的旧路径。
一个只增不减的代码库，无论写得多干净，都会在某天变得不敢改。

### 8.2 每次迭代净减少一项人工动作

迭代文档最后一行写：**本版减掉了哪个人工动作**（记到 §10 的账本）。
例：`v0.33` 减掉"手工核对轨迹点数"；本次减掉"每次会话手工读 6 个文件"、"手工跑 6 项检查"、"手工回想该跑哪些测试"。

减不出来，说明这版只是在加功能，没在变简单——可以接受，但要记账，不能假装。

### 8.3 资产三命运（每 5 版评审一次）

| 命运 | 判据 | 动作 |
|---|---|---|
| **机器化** | 这个动作每版都要做，且已重复 ≥3 次 | 收进 `tools/`，接进闸门/钩子 |
| **文档化** | 需要人判断、无法断言 | 写成一条可判定约束，进 `CONSTRAINTS` |
| **删除** | 连续 5 版没发挥作用 / 已被替代 | 移入 `tools/legacy/` 或直接删（git 有历史） |

判断标准只有一句：**它能回答「防住过什么错误、省过什么成本」吗？** 答不上就进观察名单。

### 8.4 本版退役记录

| 资产 | 处置 | 理由 |
|---|---|---|
| `validate.py` / `check_invariants.py` / `compare.py` / `make_baseline.sh` / `inspect_tpl.py` | → `tools/legacy/` | 模板骨架，从未接线（`REQUIRED=["关键列1"]`、`main.py --out` 不存在）。留在根目录会被 AI 当入口读 |
| `doc/001-参数sheet配置规范.md` | → `doc/025-…` | 与 `doc/001-迭代文档模板.md` 撞号，索引门 FAIL |
| 模板七门中的门 1/2/3（双跑对比） | 不启用 | 本项目无输出目录，会永远 SKIP |
| 常驻守护进程 / 自动修复 / 自动重建基线 | 不做 | 违背轻量；自动改代码会把错误固化成标准 |

### 8.5 为什么这套能「越久越简单」

- **知识不在人脑里，在约束和断言里**：新人/新 agent 不需要听 30 分钟背景，读 4KB 简报即可开工。
- **错误只犯一次**：每次事故都被下沉成规则 → 断言 → 钩子，同一类错误第二次出现时机器会先叫。
- **改动的影响面被结构限制**：任务卡范围 + 任务卡租约 + 入口文件集中管理，让"改一处坏一片"的概率持续下降。
- **成本可度量**：上下文 KB、闸门耗时、返工轮数都是数字，涨了就能立刻看到，不会温水煮青蛙。

## 9 手册自己怎么成熟

这份手册不是写完就完的文档，它有自己的生长规则：

1. **三级下沉，不跳级**：事故 → 一句约束（1 分钟）→ 一条断言（10 分钟）→ 一个钩子（5 分钟）。
   先写复杂钩子再想防什么，必然长出无人维护的资产。
2. **每版一行 changelog**（见附录 D）：写清「新增/反转/退役」，没写等于没发生。
3. **冷静期**：新规则 7 天内不加码。规则堆积比没有规则更糟——AI 会开始挑着遵守。
4. **每 5 版做一次减法**：从附录 D 里挑一条最没发挥作用的规则/工具删掉，并说明理由。
   **一份只增不减的手册，会在半年后变成没人读的摆设。**
5. **被推翻的规则不删**，标「已被 Cxx 反转」并留反转理由（学习价值 > 整洁）。

## 10 指标（都能用命令算，不靠感觉）

| 指标 | 怎么算 | 目标 | 现状 |
|---|---|---|---|
| **上下文开销** | 门 6 输出（入口 KB + brief B） | 入口 ≤36KB，brief ≤4KB | 30KB / 3.9KB |
| **闸门拦截率** | `git log --grep` 统计「首次提交被 pre-commit 拦下」的次数 / 总提交 | ↑ | 待积累 |
| **交接完整率** | 带 `Refs: doc/NNN` 的提交 / 总提交 | ≥95% | 本次起由 commit-msg 强制 |
| **返工轮数** | 同一任务的 `git log` 提交数（任务卡 id 出现在提交信息里） | ≤2 | 待积累 |
| **人工动作数** | 每版迭代文档「减掉的人工动作」累计 | 每版 ≥1 | v0.34 起记账 |
| **并行冲突数** | `task check` 拒绝认领的次数 | 越少越好（说明边界划得清） | 0 |

一条命令看现状：

```bash
bash tools/run.sh --fast        # 上下文/索引/密钥/语法
bash tools/ai.sh task list      # 并行任务与范围重叠
```

## 11 反模式清单（看到就停手）

| 反模式 | 为什么危险 | 替代 |
|---|---|---|
| 「你检查一下有没有问题」 | 没有判据，只能生成乐观报告 | 指向具体门/文件/断言 |
| 用 `grep` 中文输出代替结构化判定 | 改一句文案就静默失效（漏报 > 误报） | JSON + `id/status` |
| 人工通读全量 diff 当评审 | 注意力撑不过 300 行，等于没审 | 评审单看风险与约束，diff 只抽样 |
| 改断言/改约束让闸门变绿 | 把 bug 固化成"标准" | 先归因，再修根因 |
| 自动修复 + 自动提交 | 错误被批量固化 | 只出分诊单，人拍板 |
| 手改 `brief/review/TRIAGE/json` | 制造会过期的假状态 | 改源文件，重跑命令 |
| 并行改同一文件 / 同一入口文档 | 覆盖、半合并、判断账分叉 | 任务卡租约 + 集成者统一落盘 |
| 状态只写在聊天记录里 | 换会话即失忆 | `STATE.md` + `brief` |
| 为"规范"再加一份文档 | 两份真相，且没人读 | 升级为约束或断言，删掉文档 |
| 一版塞 5 个需求 | 归因不可能，回滚不可能 | 1–3 个，超出拆版 |
