## 1. 需求背景（用户原话）

> 在模板的某个环节，在附件列，添加上传文件至少 3 张，上传一个附件图片，上传一个 PDF 的，
> 这样的配置和测试

落地为：模板「附件」列支持 `上传:标签@下限(类型下限)`，服务端真正接收文件并在提交时校验；
选「流程-日常巡护」第 1 环节做样例（独立流程，随时可测，不影响主线）。

## 2. 验证结果（改前数据对比/报错现场）

- 改前 `parse_att` 只认 `上传:标签@N`，没有类型下限；前端 `upload` 分支只往留痕里写文件名，
  **文件根本没有上传**，`/flow/batch` 也**完全不校验附件**——不传附件照样能提交。
- 模板「附件」列原值：巡护第 1 环节为空；改后为 `上传:巡护资料@3(图片≥1;PDF≥1)`。
- 浏览器实测（v0.42 前）：`上传` 按钮点完只出现文件名，服务端 `flow_att` 无行，换台设备即丢失。

## 3. 设计方案（逻辑+口径依据）

**DSL**：`上传:巡护资料@3(图片≥1;PDF≥1)`

| 片段 | 含义 |
|---|---|
| `上传:` | 真实文件上传（服务端存 `data/attachments/<wid>/`，C07 只约束照片，不动扫描件口径） |
| `巡护资料` | 标签，上传接口只接受模板声明过的标签 |
| `@3` | 数量下限 |
| `(图片≥1;PDF≥1)` | 类型下限；括号内用 `;` 分隔，`split_top` 括号感知所以不会被外层拆分 |

口径：

- **魔数优先**：JPG `FF D8 FF`、PNG `89 50 4E 47`、WebP `RIFF....WEBP`、PDF `%PDF-`；
  扩展名和浏览器 mimetype 都不作数（C13 服务端权威）。
- **客户端 count 不作数**：上传件必须按 id 在 `flow_att` 找到本工作簿/行/流程/环节/标签的行，
  缺一行即视为「引用无效」；`rec_no` 只能是 0（未认领）或本次记录，**同一文件禁跨记录复用**。
- **下载要登录**：`GET /api/attachments/<id>` 走 `login_required`，路径做 `relative_to(ATT_DIR)`
  防穿越；不产生公开直链。
- **上传上限 10MB**：扫描件够用，也压住磁盘占用；照片仍走手机本机（C07），不进这个通道。
- **purge 连带清文件**：删工作簿时删 `flow_att` 行 + `ATT_DIR/<wid>/` 目录。

## 6. 反转记录（反转了哪条旧决策，为什么）

1. **反转「上传只留痕」**：旧模板对 `上传:` 只记文件名，文件从未离开手机，提交闸门也看不到。
   现改为真实上传 + 服务端按 id 校验，附件成为可核验的提交材料。
2. **反转「附件只校验数量」**：v0.38 只认 `@N` 张数；现在增加类型下限（图片/PDF），
   防止「3 张图片冒充巡护资料」。
3. **反转「附件可自由复用」**：同一附件 id 绑定 rec_no 后，不能再报给另一条记录，
   避免一份材料反复交差。
