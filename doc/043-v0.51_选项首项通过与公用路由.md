# 043 - v0.51 选项首项通过 + 项目类型留空公用

## 1. 需求背景（用户原话）

> 「巡护流程是公用的，是否路由可以不填项目类型？同时兼容没有 项目类型 项目，路由里面不写项目流程，都执行？先想合理性是否最优，是再执行」

> 「撑杆 覆膜 和正确值是第一个 影响后面的 通过，这个怎么设置？」

> 「修改模板和程序 添加 →首项通过 ，不正确 不合符 为默认不通过 不用添加，巡护情况 不添加」

## 2. 验证结果（改前数据对比/报错现场）

- 选项选哪项都不影响结论：`main.py` 只从「是否通过」控件取 verdict（L1295-1299）；
  `static/flow.js::v2JudgeFails` 只检查 `c.judge`（L1201-1218），而 `flow_tpl._control`
  只给数值/百分数/自动控件生成 judge（L171-195）。撑杆/覆膜/巡护的选项都只是记录值。
- 路由空项目类型按空字符串严格匹配：`flow_tpl.routes_for` 旧实现
  `_s(r['type']) == _s(project_type)`，空路由只命中空数据类型；单测 K3 就是这个口径。
- 线上 workbook 16（蔡师版）149 行、5 条路由；线上静态资源仍是 `?v=0.48.0`。

## 3. 设计方案（逻辑+口径依据，引用证据文件）

**选项判定**
- 参数页新增 `选项判定=首项通过`：模板级默认，所有「选项」控件首项=通过、其余=不正确并拦「通过」。
- 控件级开关写在右括号后：`选项(...)→首项通过` 单独启用、`→不判定` 退出默认（巡护）。
- 未选择仍只走必填；底部「不通过」不受影响，可提交并写备注（沿用 C34 的「只拦通过」）。
- 不采用「程序全局默认首项通过」：旧模板会静默变行为，非判定型下拉会误拦合法通过。

**公用路由**
- `流程路由` 的「项目类型」留空 = 公用，适用于所有项目类型。
- 同一流程同时有公用和专用路由时专用优先，且只保留一条，避免界面出现两个同名流程。
- 数据表没有「项目类型」列时全部路由可用（C35 原行为）。
- 空项目类型数据、以及「某类型只有公用巡护没有主线」在体检中报 FATAL。

## 6. 反转记录（反转了哪条旧决策，为什么；无则写「无」）

- 反转 **C35①「有列但空值仍严格」**：改为「项目类型留空 = 公用」。原因：巡护是跨类型公用流程，
  每类型复制一行会漂移；空项目类型数据本身应判错，不存在真实兼容场景。
- 反转 **C37②「选项只是记录」**：增加模板级「首项通过」。原因：撑杆/覆膜等定性项需要拦住
  「选了不达标还点通过」；巡护用 →不判定 明确退出。
- 保留：选项不预填、原表口径提示、只拦「通过」、不通过可写备注提交。
