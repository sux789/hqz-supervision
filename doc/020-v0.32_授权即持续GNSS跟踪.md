# 020 — 授权即持续 GNSS 跟踪（v0.32）

> 目标：**只要 App 拿到定位权限，就持续采集轨迹（仅 GPS 卫星定位），完全放弃网络定位**。
> 用户原话：「实现只要应用授权就 GNSS 持续跟踪，完全放弃网络定位」。
> 口径：2026-10-14 ｜ 参照版本 v0.31（app versionName 0.9 / versionCode 9）

---

## 〇、一句话结论

采集的生死权从「网页按钮」移到「原生侧 + 授权状态」：冷启动 / 回前台 / 授权回调三处自启（幂等），
页面只是**观察者 + 上传者**；点先落原生文件缓冲（进程死了也不丢），网页按水位线切段上传。
v0.19 起原生就只注册 `GPS_PROVIDER`，本轮把最后一条网络定位通道——WebView `watchPosition` 回退——删掉。

## 一、需求

| # | 需求 | 原状态（v0.31） | 目标 |
|---|---|---|---|
| R1 | 授权即采 | 必须进工作簿详情页手点「◎ 轨迹」才开采 | 权限 granted ⇒ 原生自动开采，无需页面/按钮 |
| R2 | 持续 | 切小班/开始录像/返回列表会**停止**采集；页面重载丢实时流 | 三件事都不停采（只切段上传）；页面重载无缝续采 |
| R3 | 仅 GNSS | 原生已只收 GPS；但无插件时回退 `watchPosition`（fused，混基站/WiFi 点，GCJ-02，精度 50~1000m） | 删除回退；非 App 环境明确不可用 |
| R4 | 数据不丢 | 点存 localStorage（页面重载不丢，进程死丢） | 点存原生 `files/track_buffer.csv`（进程死也不丢）+ 网页水位线防重 |

**明确不做**（写进待确认，不替用户拍）：

- **开机自启（BOOT_COMPLETED）**：本轮不做。重启后需打开一次 App 即恢复持续采集（授权是持久化的）。
  要做的话需把采集引擎搬进 `BgLocationService` + 加 `BootReceiver`，属于下一轮（见 §七）。
- **打卡 / 照片水印坐标**：仍走 Web `getCurrentPosition`（一次性定位，非轨迹链路；且 v0.30 起水印优先取原片 EXIF）。
  室内无 GPS fix 时打卡要可用，不能一起改成纯 GPS。
- **手动彻底停止采集**：按需求口径「只要授权就持续」，不提供停止按钮；停止途径 = 系统里撤销定位权限
  （原生检测到即停采，缓冲文件保留）。电池代价由 location 型前台服务的常驻通知明示。

## 二、验证（怎么算做对了）

1. 冷启动 App（已授权）→ 通知栏出现「轨迹持续记录中」→ 走动 1 分钟 → 无需点任何按钮，通知计数上涨。
2. 息屏 / 切后台 / 进别的 App 10 分钟 → 计数继续上涨（location 型前台服务）。
3. 详情页之间跳、返回列表、开始录像 → 采集**不停**；有 ≥2 点时自动结算上传一段 GPX，计数归零续采。
4. 杀掉 App 进程再打开 → `drain()` 取回进程死前录的点，接上续采（文件缓冲生效）。
5. 关掉系统 GPS 开关 → 收到「GPS 已关闭」提示；打开后恢复。
6. 桌面浏览器打开网页 → 「◎ 轨迹」点击提示仅支持 App（无任何网络定位点入库）。
7. 管理后台能看到上传的 GPX，点数与通知计数量级一致。

## 三、设计

### 3.1 组件职责

```
┌──────────────────────────── App 进程 ────────────────────────────┐
│ BgLocationPlugin（桥接层，随 Bridge 存活，页面重载不死）            │
│   · ensureTrackingIfPermitted()：load()/handleOnResume()/授权回调   │
│   · GPS_PROVIDER 监听（1000ms / 2m）→ 内存缓冲 + CSV 文件           │
│   · startWatcher=附着（幂等） / drain / status / clearBuffer        │
│   · notifyListeners('gpsState')                                     │
│ BgLocationService（location 型前台服务壳：常驻通知保进程优先级）      │
│   · 静态助手 ensureChannel/build/updateNotification（插件也用来更新）│
└──────────────────────────────────────────────────────────────────┘
        ↑ drain/status/clearBuffer          ↑ 实时点流（callback）
   static/app.js（观察者 + 上传者，无采集逻辑）
```

### 3.2 关键决策

| 决策 | 选型 | 理由 |
|---|---|---|
| 采集引擎放插件还是服务 | **插件**（现状延续） | 插件随 Bridge 存活，天然跨页面重载；搬进服务是为开机自启，本轮不做（§一） |
| 缓冲介质 | 内存 `List<double[]>`（cap 5 万）+ `files/track_buffer.csv` 同步追加 | CSV 一行 5 字段（lat,lng,ele,acc,timeMs），~40B/点；5 万 ≈ 14h @1Hz；文件超 10 万行压缩回内存尾 5 万 |
| 网页怎么不重不漏 | `trackSeenT`（会话内按 t 去重）+ `hqz_sup_track_upto`（localStorage 单数字水位线） | drain 回填与实时流有交叠（同一 fix 两条路都到），按 GPS 时间戳去重；水位线挡住「已上传过的点跨重载复活」 |
| 上传失败怎么办 | 不清缓冲、不清会话，toast 提示重试 | 林区无信号是常态；清了就等于丢数据 |
| 上传成功后 | `clearBuffer()` + 会话 `slice(快照长度)`（迟到点留给下一段） | 上传窗口内到的点既在会话也在缓冲；清缓冲后它们仍在会话，仅「上传成功瞬间恰好重载」会丢几秒点（可接受，记录在案） |
| 通知更新 | 10s 节流 + GPS 开关/启停即时 | 1Hz notify 太频 |
| 权限弹窗归属 | 只有 `ensurePermissionsUpfront`（登录后一次，localStorage 记问过） | 插件不再弹窗（C18 不重复打扰）；没权限时 startWatcher 直接 reject |

### 3.3 状态机（原生）

```
            load()/resume()            权限 granted
   未采 ─────────────────────► 采集中 ─────────────►（GPS 无 fix 期间不出点，轨迹空白）
     ▲                          │
     │ 权限被撤(resume 检测)      │ stopWatcher()/handleOnDestroy()
     └──────────────────────────┘
  撤销权限：removeUpdates + stopService，**缓冲文件保留**
```

## 六、反转链

- 2026-08-25 用户决策「去掉网络兜底，只收 GPS」→ 本轮把 WebView 侧的 fused 回退也删了，**该决策全链路闭环**。
- v0.19「原生优先、Web 回退」→ 反转为「原生唯一」，回退分支整体删除（不是加开关）。
- 「轨迹按钮 = 开始/停止」→ 反转为「按钮 = 结算上传当前段」，开始/停止的概念消失。

## 七、部署与后续

- 网页侧随 `./deploy.sh` 上线；原生侧需出包（versionCode 10 / versionName 0.10）。
- **新老版本混用窗口**：新网页 + 旧 APK（无 `status/drain`）→ 按钮点击提示「需要新版 App」，不崩；旧网页 + 新 APK → 旧网页的 `stopWatcher` 会停采，但下次回前台自启补上，行为可预期。建议两边同步发。
- 后续项（本轮明确不做）：① BOOT_COMPLETED 开机自启（引擎搬服务 + BootReceiver）；② 通知栏加「结算上传」快捷按钮；③ 缓冲区溢出时本地告警。
