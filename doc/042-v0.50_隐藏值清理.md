# 042 - v0.50 迭代记录_手工流程走查与隐藏值清理

## 1. 需求背景（用户原话）

> 模拟手工填写一个完整小班流程，如果有问题自动改进

按现场操作顺序在本地 8720 走完整条链路：打开小班 → 整地 → 回塘底肥 → 栽植撑杆覆膜 → 完工验收 → 日常巡护 → 导出 → 后台进度。全部控件按界面逐项填写（含拍照、附件上传、通过/不通过），把中途卡住或结果不对的地方当作问题修掉。

## 2. 验证结果（改前数据对比/报错现场）

走查工作簿 `wid=1191`（XP-1320，人工造乔木林，149 小班）与新建的 `wid=1246`：

- **隐藏备注串到下一次「通过」**（数据错误，可复现）：
  1. 整地选「不正确」+ 就地备注，点「不通过」，填流程备注 `现场复核未达标，要求返工整改` → 提交成功；
  2. 复核整改后改回「正确」，点「通过」→ 提交成功，但 `flow_records` 里仍留着
     `step_no=7 / factor=备注 / value=现场复核未达标，要求返工整改 / result=通过`；
  3. 导出「流程填报」会把这条备注挂在「通过」记录上，读起来前后矛盾。
     根因：`/flow/batch` 按客户端提交的 `values` 原样落库，隐藏控件（备注/就地备注）没展开时也照存；前端 `submitV2` 也把 `F.v2val` 整份提交。
- **导出「流程填报」顺序与现场不一致**：模板「流程路由」把独立巡护序号写成 0，导出按表序排，巡护排在整地之前；App 下拉与后台进度却是主线在前、巡护最后。
- **环节序号分母含隐藏行**：整地界面可见 6 项，卡片写 `1 / 8 … 6 / 8`（7=隐藏备注、8=结论按钮），现场会误以为还有两项没填。

## 3. 设计方案（逻辑+口径依据，引用证据文件）

- 隐藏控件是否出现已有唯一判定：服务端 `_hidden_shown(c, values)`（main.py:1197，按 `show_on`；老模板回落「结论=不通过」），前端 `v2CtrlShown(c)`（flow.js:670）同口径。**未展开 = 本次没有这个字段**，旧值不能跟提交走。
- 服务端是边界（C13）：先按 `_hidden_shown` 算出本次未展开的 `(环节, 控件)`，删除该 `rec_no` 的旧行，再落库；旧客户端即使整份提交也不会污染。
- 前端同步剔除：`submitV2` 提交前把未展示的隐藏值从值对象里删掉，草稿与界面保持一致。
- 导出顺序复用 App/后台的排序口径：主线按路由序号，独立流程最后（`_progress_flows` 已有同样规则），不改数据，只改展示顺序。
- 序号只数实际渲染的卡片：隐藏备注在展开时（结论=不通过）才成为一张卡片，序号/分母随渲染变化，不再用模板行号。

## 6. 反转记录（反转了哪条旧决策，为什么；无则写「无」）

1. **反转「提交=客户端整份状态原样落库」**：隐藏备注只在展开时存在，未展开仍提交会把上一次不通过的说明带到通过记录，违反「同一事实只算一次」；改为服务端按 `show_on` 清理 + 前端剔除。
2. **反转「导出明细按路由表序」**：路由表把独立流程序号写成 0，导致巡护排最前；改为与 App/后台一致（主线在前、独立最后）。
